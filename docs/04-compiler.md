# 编译器：JS 源码怎么变成字节码（白话版）

> 前置：字节码篇讲了"字节码是一份简单指令清单"。本篇讲这份清单是怎么从你写的 JS 一句句造出来的。

## 第 1 步：编译器干一件什么事？

编译器（Compiler）的活儿就一句：**把"语法树"（代码的结构）翻译成"字节码清单"**。语法树是上一步"语法分析"整理出来的——它已经知道"谁先算、谁属于谁"，编译器只要照着这棵树，一步一步 emit 出对应的指令就行。

你可以把编译器想成一个**翻译员**：左边听着"语法树"念的"先算这个、再调用那个"，右边就在字节码清单上记一行对应的简单指令。

下面四个"大招"是编译器最该懂的概念，挨个讲。

## 第 2 步：大招一——把变量名换成"第几号格子"（作用域与槽）

你在代码里写 `var x = 1`，但字节码里没有"x"这个名字，只有"第 0 号格子"。编译器在进到一个函数时，会开一个"变量登记表"：

```kotlin
val scope = Scope(outer = parentScope)   // 新建一层登记表
scope.declare("x")                        // x → 占用下一个编号，比如 0
```

之后所有用到 `x` 的地方，都变成 `LOAD_LOCAL 0` / `STORE_LOCAL 0`。

关键点有两个：
- **一层套一层**：进函数、进 `{}` 块就新开一层登记表；查变量从里往外找（这就是"作用域链"）。
- **格子号只在自己函数内有效**：子函数里的 `x` 占它自己的 0 号格，跟外层没关系。所以局部变量是"私有财产"，不会漏到父函数里（字节码篇第 6 步讲过）。

> 一句话：**编译器把"好记的变量名"翻译成"好查的格子号"**，VM 只需要按号存取。

## 第 3 步：大招二——闭包：内层函数记住外层变量（upvalue）

这是新手最晕的。例子：

```js
function outer() {
  var x = 1;                 // 外层变量
  function inner() { return x; }  // 内层函数用到了 x
  return inner;
}
```

`inner` 以后在 `outer` 已经结束之后，还能用到 `x`。这种"记住外层变量"的能力叫**闭包**。

KJS 怎么做？外层函数 `outer` 在编译时，发现 `x` 被内层 `inner` 用了，于是把 `x` 装进一个**共享盒子（Upvalue）**。所有内层函数看的是**同一个盒子**，而不是各存一份。

翻译成字节码后：
- 外层 `STORE_LOCAL` 写格子时，如果发现这个格子其实是个盒子，就改成"写进盒子里"：`locals[a] is Upvalue -> 盒.value = v`。
- 内层读 `x`，变成 `LOAD_UPVAL`（从盒子里读），而不是 `LOAD_LOCAL`。

> 一句话：**闭包 = 把被记住的变量放进一个共享盒子，内层函数通过盒子读写它。**

## 第 4 步：大招三——提升（hoisting）与声明顺序

JS 里 `var` / `function` 有"提升"现象：函数可以在"声明之前"就被调用。比如：

```js
foo();              // 合法：foo 被提升了
function foo() {}
```

编译器对此的处理很朴素：**一进函数，先把所有 `var` 和 `function` 声明登记进格子表（占位）**，然后再真正编译函数体。这样无论函数体里哪一行用到 `foo`，格子表早就有它了。函数声明还会顺手 emit 一条 `MAKE_CLOSURE` 把"函数对象"造出来放进格子。

> 一句话：**进函数先"点名"所有变量/函数，再开始翻译身体。** 这就是提升的本质。

## 第 5 步：大招四——跳转修补（emit / patchA / patchB）

第 2 步到第 4 步是"顺序翻译"。但 `if` / `for` / `while` 这类要"跳来跳去"，就必须用"跳转修补"（字节码篇第 4 步详细讲过）。

举个 `if (a) { b(); }` 的例子，编译器是这么干的：

```kotlin
emit(Op.LOAD_LOCAL, slotOf("a"))     // 把 a 压进盘子
val jf = emit(Op.JF, 0)              // 先占个坑：a 为假就跳走，目标先填 0
compile(b());                        // 翻译 if 身体
patchA(jf, code.size)                // 回头把坑填上：跳到"身体之后"
```

`JF` 是"为假就跳"。写它时还不知道"身体之后"在第几行（因为身体还没翻译），所以先填 0 占坑，等身体翻译完，用 `patchA(坑的行号, 真正的行号)` 把坑补上。菜谱里"转到第 ___ 步"的比喻就是它。

`for` 循环同理：循环体末尾 emit 一条"跳回循环头"的 `JMP`，头部的"条件不满足就跳出"用 `JF` 占坑修补。

> 一句话：**跳转目标未知时先占坑，等知道了再回填。这就是 emit / patchA / patchB。**

## 第 6 步：顺手做的"语法糖"展开（class 等）

有的 JS 写法其实是"另一层写法的简写"，编译器会先把它展开成基础指令，叫"脱糖（desugar）"。

最典型的是 `class`。JS 的 `class` 本质上就是"构造函数 + 原型"。所以编译器把：

```js
class C { constructor(n){ this.n = n; } m(){} }
```

翻译成大致这样一组指令（白话版）：
1. 造一个函数 `C`（就是构造函数）；
2. 给 `C.prototype` 挂上方法 `m`（`STORE_PROP "m"`）；
3. 构造函数体里 `this.n = n` 变成 `STORE_PROP "n"`（往对象上挂属性）。

也就是说，**你写的 `class` 在字节码里并没有专门的指令，全是"造函数 + 挂属性"组合出来的**。这样字节码指令集反而能保持很小（约 70 条就够）。

> 一句话：**高级写法在编译期被拆成基础指令，VM 只认最基础的那些。**

## 第 7 步：编译器的整体产出

编译器跑完，每个函数（含最外层程序）都得到一份自己的字节码（三条并排数字列 + 池子 + 子函数池），然后 `freeze` 成只读定稿，交给 VM 执行。

## 第 8 步：常见坑 / 设计取舍

- **占坑必须立刻记行号**：占完 `JF` 坑后若又 emit 了别的指令，行号总数变了，必须马上用 `code.size - 1` 记下坑在哪，否则补错行。
- **格子号与`this`**：方法调用时 `this` 通过 `CALL_METHOD` 传入，不是普通局部变量；普通函数调用 `this` 是全局对象。
- **闭包盒子要共享**：多处捕获同一外层变量必须指向**同一个**盒子对象，否则内层改了外层看不到。
- **脱糖要彻底**：`class` / 展开运算符等若脱糖不全，会留下 VM 不认识的写法。

## 第 9 步：接下来读什么

读完本篇，去看**虚拟机篇（05-vm）**：字节码清单是怎么一行行跑起来的，函数怎么调用、参数怎么传、闭包盒子怎么被读写、异常怎么接住。
